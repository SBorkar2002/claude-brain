## The core rule

**Every line of the script gets a shot that proves it.** Generic SaaS video asserts things over a slow zoom on a gradient. You show the receipt for each claim. That single rule is most of the differentiation, and it's mechanical enough to hand to someone else.

Corollary: if a line can't be assigned a proof shot, the line is wrong — send it back.

## Shot vocabulary — 7 primitives

Everything you're handed decomposes into these. Nothing else gets invented per-video.

| # | Shot | Proves | Looks like |
|---|---|---|---|
| 1 | **Terminal** | it actually runs | real command, typewriter in, real output |
| 2 | **File** | it's a real artifact, and it's small | path visible, content writing itself |
| 3 | **Diagram build** | mechanism / structure | boxes + arrows drawn in sequence, never all at once |
| 4 | **Split** | difference | before/after or wrong/right, side by side |
| 5 | **Stat** | scale or cost | one number landing hard, everything else gone |
| 6 | **Strike** | correction | wrong definition struck through, real one replaces it |
| 7 | **Real capture** | it's not staged | actual screen recording, unretouched |

Seven is the cap. The constraint is the style.

## The mapping

Every VO line is making one of six kinds of claim. This is the lookup table:

| Line is… | Shot |
|---|---|
| defining a term | Strike (6) |
| explaining how something works | Diagram build (3) |
| stating a result | Terminal (1) or Real capture (7) |
| quantifying cost/time/scale | Stat (5) |
| contrasting two things | Split (4) |
| telling you what to do | File (2) |

That's the whole decision. It removes taste from the per-video work, which is exactly what makes it scalable.

## How a handed script becomes a video

1. **Annotate.** Go line by line, tag each with a claim type. Takes 10 minutes.
2. **Assign.** Claim type → shot, via the table. You now have a shot list.
3. **Rhythm check.** Fix violations (below) before touching a render.
4. **Assemble** from templates.
5. **Captions** per your existing system — CC band bottom, emphasis above it.

Steps 1–3 happen in a doc. If you're opening HyperFrames before step 3 is done, you'll rebuild.

## Rhythm rules

- No two identical shots adjacent. If the table gives you three diagram builds in a row, the script has three explanations in a row — that's a script problem, flag it.
- Shot changes at minimum every ~4s. Longer than that and it reads as a slideshow.
- Cut on the word the line hinges on, not at the end of the sentence.
- Silence is allowed. A stat landing in silence hits harder than one with VO over it.
- One idea per shot. If a shot carries two, split it.

## The template library — this is the actual answer to "how do we execute"

Build each of the 7 primitives **once**, properly, as a parameterized HyperFrames scene. Then every new script is *assembly*, not authoring.

Each template takes props and nothing else:
- Terminal → `command`, `output[]`, `typing speed`
- Diagram → `nodes[]`, `edges[]`, `reveal order`
- Stat → `number`, `unit`, `label`
- Split → `left`, `right`, `verdict`
- Strike → `wrong`, `right`
- File → `path`, `lines[]`
- Capture → `video`, `annotations[]`

Target: a 60-second short is under 90 minutes of work once the library exists. If it isn't, a template is under-built and needs another pass. That's your real success metric — not how any single video looks, but how fast video #20 ships.

## Anti-SaaS rules

These are what stop it drifting back to generic:

- No gradients, no glassmorphism, no floating cards with drop shadows on a purple background.
- Nothing rotates or tilts — ever. (Your standing rule; it also happens to be the single strongest anti-corporate signal.)
- Every surface is either **real** (monospace, terminal, actual capture) or **drawn** (flat, honest, hand-built diagram). Never the polished-fake middle.
- No slow zoom on a static UI. If the screen isn't changing, cut.
- No stock footage, no abstract "AI" imagery, no glowing brains or neural nets.
- Type does the work. You already have the scale and tokens locked — that's the system.

## Lock before you build templates

Four decisions, and changing any of them later means rebuilding the library:

1. **Aspect ratio strategy** — build 9:16 native and letterbox up, or 16:9 native and crop down? Affects every template's safe area.
2. **Caption band height** — fixed reserve at the bottom of every template, so nothing ever collides.
3. **Whether the host appears** — if yes, every template needs a corner-safe zone reserved now, not retrofitted.
4. **Terminal fidelity** — real recordings or simulated? Real is more credible, simulated is faster and always legible. Pick one and never mix, because the audience will spot the seam.

## Read the request first

Calibrate treatment, not whether to design. A doc deserves the same craft as a landing page — what changes is the treatment that craft is delivered in.

Many requests call for a more utilitarian treatment: a plan, a memo, a demo. Make it polished: include real typographic hierarchy, considered spacing, and a proper palette, but avoid over-designing. Most pages do not need a flashy, gigantic hero. Keep flourishes tasteful and limited.

Some requests call for an editorial treatment: a landing page, a game, an app or tool they'll keep or share.

When unsure: a well-composed page is never the wrong answer; an over-designed visual identity sometimes is.

Fundamentals below apply to everything. The editorial process after that runs only when the read above says so.

## Fundamentals for every artifact

**Honor what's already there** Look for an existing design system first — CLAUDE.md, a tokens or theme file, existing component styles. When one exists, apply it; everything below fills gaps and never overrides. Precedence is always: the user's own words, then the project's existing system, then your choices.

**Ground it in the subject.** If the subject isn't already clear, pin it: one concrete subject, its audience, and the page's single job. The subject's own world — its materials, instruments, vernacular — is where distinctive choices come from. Build with real content throughout, never lorem.

**Pair typefaces** Typography carries the page even when the page isn't about typography. The Artifact CSP blocks font CDNs, so don't link a webfont URL and risk a silent fallback. Instead inline the face as a @font-face data URI. Keep running text near 65 characters wide; set a type scale and stay on it; give headings `text-wrap: balance`, body text room to breathe, and uppercase labels a touch of letter-spacing.

**Choose neutrals, don't default to them.** A pure mid-grey reads as unconsidered; a grey with a slight hue bias toward the page's accent reads as chosen. Pure white and near-black are fine grounds when they suit the subject — the point is that the neutral was picked, not inherited.

**Design both themes.** The page renders in the viewer's theme, and the viewer has three states, not two: an explicit choice stamps `data-theme="dark"` / `data-theme="light"` on the root element, and the default "system" setting stamps *nothing* — most viewers see the un-stamped document, where only `prefers-color-scheme` separates light from dark. Structure the CSS token-level for all three: the bare `:root` block defines the complete light palette (for a deliberately dark-first design, swap light and dark consistently through this whole pattern); `@media (prefers-color-scheme: dark)` redefines only the tokens, guarded as `:root:not([data-theme="light"])` so an explicit light choice beats a dark OS; `:root[data-theme="dark"]` redefines them again so the toggle also wins in the other direction. Style components through the tokens, never directly inside a media or `[data-theme]` block — a color whose only definition sits behind `[data-theme]` never applies in the un-stamped state, and the page renders one theme's text on the other theme's ground. Two more rules keep each theme resolving as a set: the artifact composites over a ground the viewer paints in *its* theme, so `body` must set an explicit `background` from a token — a transparent body silently borrows the host's ground; and every element that sets a color takes it from the same token set as the surface behind it, never a literal that only works in one theme. Before publishing, scan the stylesheet for any color declared only inside a media or `[data-theme]` block — that is the classic unreadable-artifact bug. Give the second theme the same care as the first — don't naively invert; keep contrast legible and the accent working on both grounds. A design that deliberately commits to one visual world (a neon arcade screen, a letterpress invitation) may stay single-theme — then skip the media query and stamps entirely but still paint the background and every color explicitly, so the page holds on either host ground; make it a choice, not an omission.

**Let layout do the spacing.** Lay out sibling groups with flex or grid and `gap`, not per-element margins that silently collapse or double. Wide content — tables, code, diagrams — gets `overflow-x: auto` on its own container so the page body never scrolls sideways. Reach for `font-variant-numeric: tabular-nums` wherever digits line up in columns.

**Avoid AI-generated design** AI-generated design currently clusters around a few looks: warm cream (#F4F1EA) with a serif display and terracotta accent; near-black with a lone acid-green or vermilion pop; broadsheet hairline rules with dense columns; a purple-to-blue gradient hero on white; Inter or Space Grotesk as the "safe" face; emoji as section markers; everything centered; `rounded-lg` everywhere; accent bar/rail on rounded cards. Where the user pins down a visual direction, follow it exactly — their words always win, including when they ask for one of these looks. Where nothing is specified, don't spend that freedom on one of these defaults.

**Build cleanly** Be cognizant of overlapping elements, cascade collisions, silent font fallbacks; visual bugs hide in the gap between source and output. Close every non-void element, double-quote attributes, give keyboard focus a visible state, respect `prefers-reduced-motion`. For generative or decorative graphics, reach for Canvas or WebGL rather than hand-authoring long SVG path data.

**CSS rules** When writing the CSS, watch your selector specificities. It is easy to generate classes that cancel each other out — a type-based selector like `.section` fighting an element-based one like `.cta` over padding and margins between sections. Structure the cascade so it doesn't silently undo your spacing.

**Writing the copy** Words are design material, not decoration. Write from the user's side of the screen — name things by what people recognize, not how the system is built (a person manages *notifications*, not *webhook config*). Active voice; a control says exactly what happens ("Publish", then a toast that says "Published"). Errors explain what went wrong and how to fix it — no apologies, no vagueness. Specific beats clever.

**Name the page like a product, not a caption.** The `<title>` is the artifact's name in the gallery and the browser tab, and it sets the reader's first impression of care. Give the page a real name: a short noun phrase, typically two to four words, specific to the subject — or, for a page that exists to answer one question, that question itself, which is then the page's name. Stop at the name — a title that carries its own explainer after a dash or colon reads as generated filler. The name must also identify the page among many: in the gallery it sits beside dozens of other artifacts, and a generic category label that could sit on any of them fails as a name just as surely as an appended explainer. When a candidate title pairs the name with a generic word — a greeting, a category, a page-type label — the name is the half to keep; a trim that drops the identity and keeps the generic word produces exactly the title that could sit on any page. And the rule removes explainers, it does not impose brevity: a multi-word title that already reads as one specific name is finished, and shortening it further only makes it generic. The one-sentence publish `description` is where the explanation belongs; the gallery shows it right under the title.

**Structure is information** Structural devices, numbering, eyebrows, dividers, labels, should encode something true about the content, not decorate it. Many generic designs use numbered markers (01 / 02 / 03), but that's only appropriate if the content actually is a sequence - like a real process or a typed timeline where order carries information the reader needs. Question if choices like numbered markers actually make sense before incorporating them.

**When it's a UI, not a document** A dashboard or tool is scanned and operated, not read top-to-bottom, so the craft shifts from typography to information design. Surface the summary before the detail; encode state in form as well as number — a pill, a chip, a severity stripe — so what needs attention reads at a glance. Semantic color (good / warning / critical) is separate from the accent hue and doesn't count as your accent. Give sparklines and charts the same care as type: an area fill, a faint grid, an emphasized endpoint. What's interactive should look interactive.

## Now the visual question — and the answer flips it

**The trap first.** The obvious move is a book: paper texture, 3D page turn, an open-book icon. Don't. Engineers don't read paper references, and skeuomorphic books read as 2015 corporate explainer — the exact opposite of your "not AI sloppy" bar.

**The reframe:** don't depict the book. **Render the actual page.**

If `phrasebook.whatever/mcp-server` genuinely exists and looks a certain way, the video isn't a metaphor for it — the video *is* that page, animated. Zero metaphor to invent, and the viewer who clicks through lands somewhere that looks exactly like what they just watched.

Which means: **design the page first. The video design is then already done.** One design system, two outputs. That also settles the which-comes-first question — the page comes first, always.

## Three scales

**Micro — the entry form.** Not a book, just the *typographic convention* of a reference entry: term in heavy weight, a slug line, numbered senses, an italic usage example. Purely typographic. Any frame set this way reads as "reference" without a single drawn object.

**Meso — the marker.** `Entry 12 / MCP server` or the URL, sitting quietly in frame. Cheap, and it's what makes video 12 feel like part of the same thing as video 40.

**Macro — the index.** This is the good one.

## The index is your signature shot

Every video opens on the sidebar — the full term list — and scrolls to land on today's entry. Terms above and below are visible. Visited ones are marked.

Three things fall out of that for free:

1. **The book is visible in every video** without anyone explaining the concept.
2. **It grows on camera.** Video 40's sidebar is visibly longer than video 3's. The compounding argument from section 08 stops being a claim in a doc and becomes something the audience *watches happen*.
3. **It's the repeated formula Anandhi described** — the equivalent of a show's title card. Same shot, every episode, instantly recognisable in a feed.

## Each format is just a different interaction with that page

This is where it gets efficient — none of these need new assets:

| Format | The visual |
|---|---|
| **Two Voices** | The sceptic types into the **search bar**. The entry loads as the answer. That's the entire format. |
| **The Ladder** | One page, **progressively expanding**. Rung 1 = the summary line. Rung 2 = the body unfolds. Rung 3 = footnotes and caveats appear. Progressive disclosure, literally. |
| **Question Compilation** | The search bar again — real queries stacking up as autocomplete suggestions, none of them with a good answer yet. |

| **Character** | Sits in the page's corner, not on a separate stage. It's reading over your shoulder, not presenting at you. |

## ASSISTANT
Yes — but the honest answer is that the tool was never the bottleneck.

## What Remotion is genuinely good at for this style

- **Flat vector.** It's React rendering SVG, so Kurzgesagt's whole aesthetic is native. No rasterisation, scales cleanly.
- **Parallax and camera moves.** Nested transforms with interpolated scale/translate gets you their layered push-ins easily.
- **Anything repeated.** Particles, crowds, orbiting bodies, a hundred dots — this is *easier* in code than in After Effects, because it's a loop instead of a hundred layers.
- **Reuse across videos.** A `<Character pose="shrug" />` component you build once and use in forty videos. This is where Remotion actually beats a timeline tool.
- **Deterministic renders.** Same input, same frames, every time.

## What's genuinely hard

- **Character rigging.** No bone system. Squash-and-stretch, limb articulation, weight — you hand-build all of it, and it's slow.
- **Shape morphing.** One shape smoothly becoming another needs path interpolation via a library; it's not free.
- **Organic timing.** Animators choreograph by feel, nudging keyframes until it *looks* right. In code you're guessing numbers and re-rendering. That loop is much slower than dragging a keyframe.

## The real bottleneck

**Kurzgesagt's cost isn't animation software. It's illustration.**

Every scene is bespoke artwork, drawn by a studio of illustrators, weeks per video. Remotion doesn't help with that at all — someone still has to draw the birds and the little guys and the planets.

So: Remotion can *animate* that style comfortably. It cannot *produce* the assets for it. Attempting their density solo gives you something that reads as bad Kurzgesagt, which is worse than not trying.

## The version that's actually achievable

**Build a component library of illustrated primitives, not bespoke scenes.**

Five to ten reusable vector components with props — a figure with pose states, a screen, a container, a few environmental pieces — plus a locked palette and layered parallax. Then each video is *composition*, not illustration.

Worth knowing: Kurzgesagt does this too. The birds recur. The little characters recur. Their consistency is partly an economy measure, and it's the part that scales down to one person. Their discipline transfers; their density doesn't.

That also means the earlier plan still holds — your page components (sidebar, entry, diff, search) are already this idea. You'd be extending the same library, not starting a second visual system.

## One alternative worth knowing

For flat vector plus heavy typography, **HyperFrames** is arguably a better fit than Remotion — HTML/CSS/SVG with GSAP timelines, no React build step, and the timeline authoring is closer to how you'd actually choreograph this. It's available in this setup.

Not a recommendation to switch. You have working Remotion knowledge and a pipeline, and that's worth more than a marginally better tool. But if the illustrated direction gets picked and you're starting a fresh component library anyway, that's the one moment where the comparison is cheap to make.

## Realistic scope, solo

With a component library in place: a 60-second illustrated piece in a day or two. Without one: a week, and it'll look inconsistent with the last one.

Which means the sequencing is the same as everything else here — **build the library first, then the videos get cheap.** The first three videos are the expensive ones, and that's worth saying out loud in the pitch so nobody judges the model by episode one.

## 2. There is no public cross-org marketplace — it's an explicit non-goal

`docs/prd/agentic-platform-product-note.md`, non-goals:

> "**Not defining a public marketplace / template exchange across orgs.** Cross-org template sharing raises IP, security, and competitive questions that dwarf this note's scope."

"Our engineer builds a skill, puts it in the marketplace, anyone can use it" isn't a thing the product does or plans to.

## 3. Your tailoring instinct was right — and it's worse than you thought

`docs/sales/locus-leave-behind.md`:

> "We derive exactly which rule files, CLAUDE.md configurations, or marketplace skills to add. **Not a generic recommendations list. Specific to your codebase, your team's patterns, your most common failure modes.**"

Org-specificity isn't incidental — it's the sales claim. A generic skill built by one engineer on camera doesn't just fail to be tailored, it **actively undercuts the pitch.** Good catch.

## Correcting the mental model

Tetriz doesn't *build* skills. It:
- **derives** org-specific prompt rules and CLAUDE.md templates from that org's own session data — Harness Recommendations: Custom, status **Done**
- **recommends** which existing third-party skills to add — marketplace, status Future
- **pushes** approved artifacts org-wide via the control plane

It's a recommender and governance layer, not a skill factory.

## Your specific questions, answered

**How complex can a skill get?** Full range. Trivial is a markdown instruction file. `skillsec` is a two-agent scanner — deterministic regex → investigator LLM → decision-maker, tuned for near-zero false positives. That range is good news for a season arc.

**How would one enhance it?** The repo already documents the pattern in waves: `disclose` ships as four sections and one hook, then gains drift checks, then a hallucination gate. That's a season structure someone else already wrote.

**Could anyone just use it?** Not via Tetriz's marketplace. Yes via npx, GitHub, and Anthropic's plugin marketplace — and the doc says the Anthropic listing is specifically pursued *for credibility*.

**What problem does it solve?** A real, quoted, customer-validated one. `context-library/users.md`:

> *"What exists already? What is available in the marketplace? What should be reused instead of rebuilt?"* — Prabu Ram, VP Eng, Razorpay

Discovery, safety vetting, and preventing rebuild-by-default across the external skill landscape.
