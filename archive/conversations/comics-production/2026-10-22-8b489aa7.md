## Why it happens

Nothing you did — this is inherent to how the model generates.

**The accent isn't a setting, it's an inference the model makes per request.** ElevenLabs' TTS is autoregressive: each chunk of audio is conditioned on the voice sample *plus everything it has already generated in that same request*. Feed the whole script and the first sentence commits to an accent; every sentence after it is anchored to that commitment. Feed one sentence alone and there's no generated audio to anchor to — only the voice reference — so the model falls back on its prior and picks whatever region of accent-space it thinks that timbre sits in.

Why Russian specifically: Indian English and Slavic English are close neighbours acoustically — syllable-timed rhythm, flatter terminal intonation, dental/retroflex stop realisations, similar vowel reductions. When the model is under-constrained, that's the nearest wrong guess. ElevenLabs documents this exact failure as a voice that will "retain its native accent, or drift between different accents" when the voice isn't firmly matched to the target language/accent — most library and Instant Voice Clone voices are only loosely pinned.

Second factor: **the seed is random by default.** Identical settings genuinely do not produce identical output, so "I didn't touch the config" and "the output changed" are both true at once.

## Fixes, best first

**1. Render the full script once, then cut it.** The condition where it works correctly is exactly the one you already found. Since you need per-segment audio for panel timing anyway, generate the whole VO as one file and split it — don't TTS segment by segment. This also protects the ≥0.4s decay tails you need at split points, which per-segment renders tend to clip.

```bash
ffmpeg -i full_vo.mp3 -ss 12.30 -to 17.85 -c copy seg_03.mp3
```

**2. If you must generate a fragment, use request stitching (API).** `previous_text` / `next_text` let you send one sentence while handing the model the surrounding script as context — it generates only your sentence, but conditioned as if mid-script. `previous_request_ids` / `next_request_ids` (up to 3 each) do the same by referencing actual prior generations, which is stronger. This parameter pair exists specifically for this problem.

**3. In the UI, use Studio, not the flat TTS box.** Studio keeps the whole document as context and lets you regenerate a single paragraph in place. ElevenLabs' own troubleshooting recommends it for anything past a few hundred characters, precisely because of accent/tone breaks.

**4. Poor-man's version of #2:** paste 2–3 sentences of preceding script before your target sentence, generate, then trim the padding off the audio. Takes 30 seconds and works.

**5. Settings that reduce drift:** Stability up to ~0.70–0.80, Style/exaggeration at 0, Speed 0.9–1.0. Higher stability means tighter adherence to the reference audio, so less accent roaming — at the cost of expressiveness, which matters if you want the "calm and natural" read to stay warm rather than flat. Also set a **seed** so a good take is reproducible and you can iterate instead of rerolling blindly.

**6. Check your model.** Must be Multilingual v2 or Flash/Turbo v2.5 — the English-only v2 models force an English accent. Note `language_code` is *not* supported on `multilingual_v2`, so that lever only exists on v2.5/Flash.

**7. Root cause, if this keeps biting:** a Professional Voice Clone trained on ~30 min of clean Indian-English audio pins the accent far harder than a library voice or Instant Clone. That's the only fix that removes the ambiguity rather than working around it.

For your pipeline, #1 is the real answer and #2 is the patch for one-off retakes of a single line.

## The thing worth knowing: `/with-timestamps`

There's a variant endpoint, `POST /v1/text-to-speech/{voice_id}/with-timestamps`, that returns `audio_base64` plus an `alignment` object with `characters`, `character_start_times_seconds`, and `character_end_times_seconds` — start and end time for *every character*. It takes all the same params, including `previous_text`/`next_text` and `voice_settings`.

That collapses your whole problem into one call. You get the single-render accent consistency *and* exact per-segment boundaries, so you never guess a cut point and never clip mid-word. Your ≥0.4s decay tail becomes a constant you add to each end time rather than something you eyeball.

Shape of it:

```python
import os, base64, json, subprocess, requests
from dotenv import load_dotenv

load_dotenv()
VOICE_ID = "PASTE_MONIKA_VOICE_ID"   # grab from the dashboard
TAIL = 0.4                            # decay tail at each split

segments = [
    "First VO line for panel one.",
    "Second VO line for panel two.",
]
full_text = " ".join(segments)

r = requests.post(
    f"https://api.elevenlabs.io/v1/text-to-speech/{VOICE_ID}/with-timestamps",
    headers={"xi-api-key": os.environ["ELEVENLABS_API_KEY"]},
    json={
        "text": full_text,
        "model_id": "eleven_multilingual_v2",
        "output_format": "mp3_44100_128",
        "voice_settings": {"stability": 0.75, "similarity_boost": 0.75, "style": 0.0, "speed": 1.0},
    },
    timeout=300,
)
r.raise_for_status()
data = r.json()

open("full_vo.mp3", "wb").write(base64.b64decode(data["audio_base64"]))
a = data["alignment"]                      # use alignment, not normalized_alignment
starts, ends = a["character_start_times_seconds"], a["character_end_times_seconds"]

# character offsets line up 1:1 with full_text
cursor = 0
for i, seg in enumerate(segments, 1):
    lo = full_text.index(seg, cursor)
    hi = lo + len(seg)
    cursor = hi
    t0, t1 = starts[lo], ends[hi - 1] + TAIL
    subprocess.run([
        "ffmpeg", "-y", "-i", "full_vo.mp3", "-ss", f"{t0:.3f}", "-to", f"{t1:.3f}",
        "-c:a", "libmp3lame", "-b:a", "128k", f"seg_{i:02d}.mp3"
    ], check=True)
```

Two notes: re-encode on the cut rather than `-c copy`, because mp3 stream-copy snaps to frame boundaries and you'll drift a few ms per segment. And clamp `t1` against the next segment's start if you don't want tails overlapping.
